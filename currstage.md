# Поточний етап: стек, структура та передавання роботи

Оновлено 19.09.2026. Це знімок локального стану `/opt/ufv` під час перевірки о 12:46–12:53 UTC, а не звіт про завершений запуск. Підстава: користувач попросив зберегти актуальні інструкції в `currstage.md` і запушити їх для команди. Код паралельно змінюється в основній сесії; перед наступною задачею звірте фактичний стан.

## 1. З чим зараз працюємо

**Продукт:** Vodafone: AI Reputation & Crisis Intelligence. Допомагаємо комунікаційній команді знайти потенційно важливі повідомлення, прочитати контекст і перевірити оригінальні джерела перед дією.

**Поточна реалізація:** тестовий Telegram-модуль із кількома Telethon-сесіями, керуванням через адміністратора, збором постів і коментарів, відновленням після простою, тематичним фільтром та обмеженими посиланнями на dashboard. Код цього модуля вже є локально; інтеграція й перевірки ще тривають.

Користувач прямо попросив зберегти й інтегрувати сайт та авторизацію, створені в іншій сесії. Тому основа інтеграції — наявний TypeScript backend і React, а збір та обробка — окремі Python-процеси. Попередній Go-кандидат не описує поточний сайт. Це не остаточне рішення для всіх майбутніх компонентів платформи.

**Важливо для GitHub:** на початку цієї перевірки `main` та `origin/main` вказували на `10723c3`; Git відстежував попередню документацію та вихідний макет. Каталоги реалізації були локальними незакоміченими файлами. Публікація цього документа сама по собі не публікує реалізацію. Якщо після `git pull` немає описаних нижче каталогів, потрібне окреме передавання коду від інтегратора; не відтворюйте паралельну реалізацію за старими README.

У цьому документі «є в коді» не означає «перевірено на реальному Telegram» або «працює за доменом».

## 2. Актуальний стек

| Частина | Поточна основа | Відповідальність |
| --- | --- | --- |
| Web | React, TypeScript, Vite, TanStack Query | Вхід, стрічка, фільтри, користувачі, налаштування Telegram, перегляд за посиланням |
| HTTP API | Node.js 22+, TypeScript, Hono, Zod | Валідація запитів, права, конфігурація workflow, читання результатів, ручні рішення |
| Авторизація | Better Auth, PostgreSQL, спільні права в `packages/shared` | Користувачі, ролі, сесії, зміна пароля, адміністрування |
| Доступ до БД у TS | `pg`, Kysely | Пули, SQL-запити; нові маршрути Telegram використовують `pg` |
| Collector | Python; контейнер Python 3.13; Telethon 1.45.0 | Сесії, канали, пости, коментарі, курсори, події змін |
| Processor | Python, psycopg, власні правила `rules-v1` | Релевантність, спам/реклама, контекст, позначення точних копій |
| Сховище | PostgreSQL 18 | Схеми `auth`, `raw`, `core`; конфігурація та стан переживають рестарт |
| Події | NATS 2 + JetStream, `nats-py` | Доставка ID збережених матеріалів, повторні спроби |
| Секрети Telegram | AES-256-GCM, спільний `TG_SESSION_KEY` для API й collector | Шифрування API hash та StringSession у БД |
| Розгортання | Docker Compose, наявний Caddy | Окремі API, collector, processor, Postgres і NATS; цільовий домен `hire.qpon` |

Версії JS-залежностей уточнюйте за `package-lock.json`, Python — за `services/collector-telegram/requirements.txt`. Збереження вже створеної авторизації та спеціалізована бібліотека Telethon — практична причина цього поділу. Переписування на Go/Rust зараз не є наступною задачею.

**LLM у поточному конвеєрі немає.** Тематичний фільтр працює правилами. Поле `summary` зараз містить початок тексту, а не AI-бриф. Тональність, ризик, прогнозування та повноцінні інциденти не реалізовані.

## 4. Логіка від адміністратора до стрічки

```text
Адміністратор → Hono API → конфігурація в core.*
                                ↓ періодичне читання
Telegram → Telethon collector → raw.items + raw.outbox в одній транзакції
                                              ↓ publisher
                                     NATS: raw.item.created
                                              ↓
                         processor ← також добирає роботу з PostgreSQL
                              ↓
                 core.mentions + core.processing_receipts
                              ↓
                  Hono API → React / обмежений dashboard
```

1. Адмін створює workflow, імпортує API ID/API hash/StringSession, додає канал, призначає йому акаунт і записує підставу дозволеного використання. Для поточного підключення використовуйте Telegram-адмінку; старий `/api/collectors/sources` не заповнює всі потрібні поля.
2. Collector читає глобальний перемикач Telegram, стан акаунта, workflow і джерела. Усі відповідні перемикачі мають дозволяти збір. Вимкнення збору не видаляє вже зібрані матеріали й не зупиняє дообробку збережених записів.
3. Кожен акаунт має окремий клієнт. Є перегляд публічних broadcast-каналів серед його діалогів; сканування обмежене 1000 діалогами. Автоприєднання до каналів та довільний імпорт приватних чатів не реалізовані.
4. Один запис `core.sources` зараз належить одному workflow й одному призначеному акаунту. `unique(kind, external_id)` не дозволяє завести той самий канал окремо в кількох workflow. Наявність багатьох сесій не означає одночасний збір одного каналу всіма сесіями.
5. Нові пости/редагування надходять через Telegram events; історія добирається polling за збереженим курсором. Для коментарів collector визначає discussion thread поста та окремо зберігає курсор коментарів.
6. До запису текст нормалізується й частково очищується від контактних даних. `raw.items` містить робочий нормалізований текст, а не повний Telegram object, HTML чи профіль автора.
7. Змінений матеріал та outbox-запис фіксуються разом. Подія містить ID; processor читає останню версію з БД. Недоступність NATS не повинна втрачати вже записаний матеріал: є добирання за receipts.
8. Processor визначає `accepted`, `review` або `rejected`, тему, бренд, причину рішення й контекст. Dashboard за замовчуванням показує прийняте; сумнівний матеріал доступний для перевірки.

Конфігурація перечитується приблизно кожні 2 секунди за кодом. Це не гарантія швидкості Telegram. `poll_seconds` задається для workflow; поточний default — 30 секунд, історія — 7 днів. Це параметри реалізації, не погоджені KPI. Live-події, доступ до discussion group, кількість каналів/гілок, простій і FloodWait впливають на фактичну затримку. Web оновлює стрічку кожні 30 секунд або за кнопкою.

## 5. Дані й контракти між компонентами

| Таблиці | Хто пише | Для чого |
| --- | --- | --- |
| `auth.*` | API / Better Auth | Користувачі, сесії, share links і share sessions |
| `core.modules`, `core.workflows`, `core.telegram_accounts`, `core.sources` | API | Конфігурація збору та зашифровані Telegram credentials |
| `raw.account_status`, `raw.memberships`, `raw.source_state`, `raw.threads`, `raw.service_status` | Collector | Спостережений стан, доступні канали, помилки, cooldown і курсори |
| `raw.items`, `raw.outbox` | Collector / його publisher | Матеріали, їх версії та надійне повідомлення про зміни |
| `core.mentions`, `core.processing_receipts`, `core.service_status` | Processor | Результати та версія виконаної обробки |
| `core.review_decisions`, `core.audit` | API | Рішення людини й журнал адміністративних дій |

Права runtime-ролей `ufv_api`, `ufv_collector`, `ufv_processor` налаштовує `deploy/bootstrap.py`. Власність розділена **за таблицями**, а не правилом «кожна схема має лише одного автора»: `core` містить і конфігурацію API, і результати processor. Нові таблиці та запити звіряйте з цими grants.

- Ключ матеріалу: `unique(source_id, source_item_id)`, де Telegram `source_item_id` має формат `peer_id:message_id`. ID коментаря належить discussion peer, а не обов'язково каналу поста.
- `parent_item_id` вказує на безпосереднього батька; `thread_item_id` — на початковий пост. `raw.threads` зберігає зіставлення поста, discussion peer, кореня гілки та курсора.
- `version` змінюється разом із збереженим вмістом; `raw.outbox` унікальний за `(item_id, version)`. Повторний незмінений матеріал не повинен створювати нову згадку.
- Подія v1: `v`, `raw_item_id`, `source_id`, `source_kind`, `fetched_at`. Великі ID в події — рядки. Текст і credentials через NATS не передаються. Версія використовується в заголовку `Nats-Msg-Id`, а processor читає поточний запис БД.
- Повторну обробку визначають `core.processing_receipts.version` та `processor_revision`. Старе `raw.items.processed_at` із міграції `0002` не є поточним механізмом черги.
- Processor використовує транзакційний advisory lock на матеріал та upsert за `raw_item_id`. Після успішного запису результату й receipt підтверджує NATS-подію. Для помилки consumer є повторна доставка; database catch-up працює окремо.
- Точні копії постів довжиною від 100 символів позначаються через hash у межах workflow. Це обмежений пошук копій, не визначення всіх перепублікацій чи незалежності доказів. Лічильники стрічки рахують записи, не незалежні підтвердження.
- Час публікації, першого отримання, останнього спостереження, редагування та обробки — різні поля. Немає виміряного часу початку реальної події чи SLA. `analyzed_at` може змінюватися при повторній обробці.

## 6. Контекст, фільтри, докази та доступ

`classification.py` містить пояснювані словники телеком-тем українською, російською й частково англійською. Спам за правилами відхиляється; можлива реклама потрапляє на перевірку. При вимкненому spam-фільтрі знайдений спам також іде на перевірку. Це евристики з можливими помилками, не виміряна точність моделі.

Коротка відповідь на кшталт «у мене теж не працює» може бути прийнята за контекстом батька. Для вкладених відповідей використовується також кореневий пост; якщо потрібного батька ще немає — `review`, а пізніше повторна спроба. Зміна батьківського матеріалу скидає receipts прямих відповідей.

`quote` зараз дорівнює збереженому нормалізованому тексту. URL формує collector із джерела та ID поста/коментаря. Це доказ походження матеріалу, але не механізм перевірки майбутніх AI-висновків. Для LLM доведеться окремо додати перевірку конкретних цитат, ID доказів і наявності підтверджених прав на таке використання.

Персональні поля авторів не записуються. Regex очищує телефони, email, @згадки й URL усередині тексту, але не гарантує вилучення всіх імен та інших персональних даних. Правило «не зберігати персональні дані авторів» залишається вимогою; для реального джерела потрібно перевірити достатність очищення. Метадані каналу та облікові записи адміністраторів — окремі сутності, їх не плутати з профілюванням авторів.

| Доступ | Поточна поведінка коду |
| --- | --- |
| `admin` | Користувачі, Telegram/workflow, credentials, share links, ручні рішення, стрічка |
| `analyst` | Стрічка та перегляд `review`/`rejected`; частина оголошених прав ще не узгоджена з маршрутами, див. наступні кроки |
| `viewer` | Читання прийнятих матеріалів |
| Share `summary` | Агреговані результати в дозволеній області; без текстів, текстового пошуку й деталей матеріалу |
| Share `posts` | Прийняті пости у дозволеній області |
| Share `full` | Прийняті пости й коментарі у дозволеній області; без адмінських можливостей |

Workflow поки не є ізольованою організацією: облікові записи з доступом до сайту не мають окремого членства в workflow. Обмеження workflow/каналів/тем реалізовані для share links. Не обіцяйте повну багатоклієнтну ізоляцію.

Самореєстрація вимкнена; користувачів створює адмін. Сесії Better Auth — у БД та HttpOnly-cookie. Share token видається у `/view#token`, обмінюється на окрему HttpOnly-cookie; у БД зберігаються хеші токенів. Область, строк і відкликання перевіряє сервер. Секрети Telegram назад через `/api/admin/state` не повертаються.

Основні точки API: `/api/auth/*`, `/api/me`, `/api/workflows`, `/api/feed`, `/api/documents/:id`, `/api/admin/*`, `/api/shared/*`, `/api/health`. Точні формати запитів — Zod-схеми в маршрутах; автоматичний OpenAPI-контракт зараз не створений.

## 7. Запуск і конфігурація

Це інструкції для продовження наявної реалізації. Спочатку переконайтеся, що її файли передані у ваш checkout.

**Локально:** Node.js 22+, PostgreSQL 18, NATS із JetStream, Python із залежностями `services/collector-telegram/requirements.txt`. Для інфраструктури є `deploy/compose.dev.yml`: PostgreSQL на `127.0.0.1:5433`, NATS на `127.0.0.1:4222`. Не використовуйте сусідню базу Warblan на 5432.

1. Створіть власний незакомічений `.env` за прикладом. Виправте `DATABASE_URL` на потрібну dev-базу та порт; встановіть `PUBLIC_URL`, `BETTER_AUTH_SECRET`, `TG_SESSION_KEY`, `NATS_URL`.
2. `TG_SESSION_KEY` — 32 випадкові байти у base64url; актуальне шифрування AES-GCM з форматом `gcm1.iv.tag.ciphertext`. Коментар про Fernet у старому `.env.example` описує попередній прототип. API та collector повинні мати однаковий ключ; не замінюйте його без перешифрування збережених credentials.
3. `npm ci`, потім `npm run db:migrate`; створення першого адміна — `npm run auth:create-admin -- <email> "Ім'я"`. Секрети не передавайте аргументами команд і не додавайте до Git.
4. `npm run dev:api` і `npm run dev:web` запускають сайт. `PUBLIC_URL` має точно збігатися з origin у браузері; Vite проксіює `/api` до backend.
5. Із налаштованим Python-оточенням запускайте `PYTHONPATH=services python -m pipeline.telegram` та `PYTHONPATH=services python -m pipeline.processor` з кореня. Ці Python-процеси **не завантажують `.env` автоматично**: потрібні експортовані змінні або Compose. Глобальний Telegram-модуль і початковий workflow створюються вимкненими.
6. Для зібраного сайту: `npm run typecheck`, `npm run build`, потім із кореня репозиторію `node --env-file=.env apps/api/dist/index.js`. Поточний static root відносний до робочого каталогу; запуск із `apps/api` не рівнозначний запуску всього сайту.

API ID/API hash/StringSession задаються для конкретного акаунта через адмінку. Старі `TG_API_ID`/`TG_API_HASH` у прикладі env не керують новим багатосесійним collector. Інтерактивний вхід Telegram за телефоном/кодом/2FA на сайті ще не реалізований; є `scripts/create_session.py`, який записує сесію у приватний файл поза Git для подальшого імпорту.

**На цьому сервері:** `deploy/compose.yml` очікує захищений `/etc/ufv/production.env`, окремі паролі DB-ролей, `BETTER_AUTH_SECRET` та `TG_SESSION_KEY`. Не копіюйте значення в документацію. `deploy/bootstrap.py` прив'язаний до цього хоста: читає захищені файли, знаходить Postgres-контейнер, виконує міграції, налаштовує права й створює першого адміністратора за потреби. Перед запуском потрібні зібрані Node-артефакти та Python/psycopg.

Очікуваний порядок deployment: build → Postgres/NATS → bootstrap → API/collector/processor → локальна перевірка API → перевірка й переключення reverse proxy. Compose підключає API до зовнішньої мережі `warblan_app` під ім'ям `ufv-api:8080`, локальний порт API — `127.0.0.1:8095`. Це залежність інфраструктури цього хоста, не вимога для ноутбука розробника.

## 8. Що фактично перевірено зараз

Під час підготовки цього документа прочитано код, міграції, конфігурації та Git-стан; перевірено список контейнерів і HTTP-відповідь домену. Інтеграційні тести, build та реальний збір Telegram у межах цього оновлення **не запускалися**.

| Пункт | Спостережений стан |
| --- | --- |
| UFV Postgres | Контейнер працює, healthcheck healthy |
| UFV NATS | Контейнер працює; це саме по собі не доводить наскрізну доставку подій |
| Контейнери API, collector, processor | Під час перевірки зупинені; готовність поточного build не підтверджена |
| `https://hire.qpon` | HTTP 307 на `/en`, відповідь попереднього Warblan-сайту; переключення не завершене |
| Інтеграційні тести | Файл `tests/test_runtime.py` існує; результат проходження актуальної інтеграції тут не підтверджений |
| Реальні Telegram-дані | Підтвердженого наскрізного тесту з дозволеним каналом немає |
| Якість фільтра, затримка, бізнес-KPI | Не виміряні |

Попередні звіти про перевірки авторизаційного каркаса або FastAPI-прототипу не є доказом готовності поточної інтеграції. Наявність коду, контейнерного образу та підготовленого тесту також не замінює результат запуску.

## 9. Наступні кроки та де їх виконувати

Власники нижче — ролі, не призначення конкретних людей: навички й доступність семи учасників ще не зібрані.

| Порядок / роль | Де працювати | Конкретний результат |
| --- | --- | --- |
| 1. Інтегратор | Git-стан, `apps`, `services`, `db`, `deploy` | Передати узгоджену реалізацію команді окремою зміною, зберегти чужу роботу й виключити секрети/локальні артефакти. Зафіксувати commit реалізації в цьому документі |
| 2. API / auth | `telegram-admin.ts`, `feed.ts`, `permissions.ts`, `bootstrap.py` | Узгодити права analyst: зараз share/review-маршрути мають admin-only `collector.manage`, хоча спільні ролі/частина UI передбачають ширші права. Перевірити кожен запит під runtime DB-роллю |
| 3. Collector | `services/pipeline/telegram.py`, `raw.py` | Перевірити пости, вкладені коментарі, рестарт, історичне добирання, редагування, видалення, FloodWait, вимкнення/ротацію сесії на дозволеному тестовому каналі |
| 4. Processor / якість | `classification.py`, `processor.py`, `tests/test_runtime.py` | Прогнати fixtures; вручну розмітити малу реальну вибірку; показати хибні спрацювання, виправлення й контекст. Узгодити повторну обробку після ручної зміни рішення батька |
| 5. Frontend | `apps/web/src/pages`, `public/console` | У браузері перевірити admin/analyst/viewer, login/logout, порожній стан, помилки, контекст, share scopes, відкликання, мобільний екран та iframe |
| 6. Інфраструктура | `deploy/*`, Caddy цього сервера | Перезібрати поточний код, завершити запуск, перевірити grants/health/логи, потім перевести `hire.qpon` на UFV з HTTPS та перевірити старі шляхи й піддомени |
| 7. Демо / документація | `currstage.md`, `docs/*`, дозволені матеріали | Записати фактичний сценарій комунікаційного менеджера, джерела, затримки й обмеження; за потреби підготувати явно позначений replay |

Окрема відома точка перевірки прав БД: `/api/admin/workflows/:id/reprocess` рахує записи через `raw.items`, а `bootstrap.py` не видає API право читати цю таблицю. Це видно зі статичного коду; виправлення й перевірку під реальною `ufv_api` ще потрібно виконати. Тест під власником БД такого дефекту не виявить.

`tests/test_runtime.py` змінює/очищує тестові таблиці та NATS stream. Запускати лише з окремою БД `ufv_checks`, окремим API, тестовими обліковими записами й окремими `UFV_NATS_STREAM`/`UFV_NATS_SUBJECT`. `UFV_TEST_ENV` вказує на приватний JSON із конфігурацією, який не комітиться. Умовою готовності є виконані assertions, а не `skip` через відсутність конфігурації. Поточні окремі перевірки правил — у `tests/test_classification.py`; результати старих `test_api.py`/`test_pipeline.py` стосувалися іншої реалізації.

Для завершення proxy на цьому хості перевірте фактичний Caddy mount; успадкована конфігурація розташована в `/opt/warblan/deploy/Caddyfile.hire`. Зміна має стосуватися маршрутизації `hire.qpon`, зі збереженням роботи інших доменів. Цей документ не виконує deployment і не свідчить про переключення.

**Мінімальний критерій готовності:** дозволений реальний пост і коментар проходять Telegram → raw/outbox → processor → авторизовану стрічку з контекстом та оригінальним URL; повторне отримання не дублює дані; вимкнення зупиняє збір; share link не відкриває даних поза дозволами й перестає працювати після відкликання; затримка та помилки пояснені; домен показує саме UFV.

## 10. Обмеження та правила для наступного агента

- Telethon не є необмеженим доступом: потрібні права акаунта/джерела, врахування FloodWait та умов використання. Поточний код зберігає cooldown; автоматичної ротації акаунтів для обходу лімітів немає.
- Коментарі можливі лише там, де є доступна discussion-гілка. Відсутність доступу не дорівнює «коментарів немає»; показуйте стан і помилку.
- Один collector-процес захищений PostgreSQL advisory lock. Це не готова горизонтальна схема розподілу акаунтів між кількома collector-репліками.
- Polling перевіряє нові записи й обмежений хвіст редагувань; повне виявлення всіх давніх змін/видалень після тривалого offline не гарантоване. Строк зберігання матеріалів, outbox і аудитів ще треба визначити.
- Інциденти, AI-брифи, семантичне групування, sentiment, оцінка кризового ризику, RSS та зовнішні сповіщення — наступні окремі задачі. Наявні поля `severity` чи ролі `incident.edit` не означають, що ці функції готові.
- Telegram-контент не передавати в LLM без окремо підтверджених прав. Не додавати профілі авторів або вигадані метрики. Перепублікації не видавати за незалежні докази; replay — за live.
- Перед роботою перечитати [AGENTS.md](AGENTS.md), цей документ і `git status`. Не перезаписувати паралельні зміни, не запускати destructive fixtures у робочій БД, не комітити `.env`, сесії, токени чи дані локальних тестів.
- Старі [STATUS](docs/STATUS.md), [CONTEXT](docs/CONTEXT.md), [PLAN](docs/PLAN.md), локальні `docs/ARCHITECTURE.md`, `docs/DEV.md` і service README частково застарілі. Зокрема, «коду немає», «collector — лише каркас», Fernet, `processed_at` як черга, SSE та готові інциденти не описують поточну інтеграцію. Для стану на цю дату починайте з `currstage.md` та звіряйте з кодом.
- [BRIEF](docs/BRIEF.md) зберігає умови хакатону, [QUESTIONS](docs/QUESTIONS.md) — питання з незмінними номерами. Реалізаційні default-значення не записувати як відповіді користувача. Точний строк, власники задач, LLM-доступи й ширший обсяг MVP залишаються відкритими.
- Після наступного змістовного кроку оновіть дату, commit реалізації, результат перевірок, фактичний стан домену та один наступний крок. Якщо перевірки не було — так і напишіть.
