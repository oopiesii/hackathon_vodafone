# API дашборда: контракт і перевірка

Додано за прямим нічним дорученням користувача. Контракт: [dashboard.ts](../packages/shared/src/dashboard.ts). `GET /api/dashboard?workflow_id=1&window=24h|7d|30d` потребує Better Auth. Admin і analyst бачать accepted/review; viewer — тільки accepted, без відсіяного, pending, загальної кількості входу й плитки шуму. Вікна 24h/7d ковзні; 30d — 30 календарних днів за Києвом включно із сьогодні. `start/end` та `href` фіксують межі для переходів до доказів.

Метрики негативу — словникова евристика, не виміряна тональність. Реакції агреговані за останнім спостереженням: NEG+IRONIC у чисельнику, SAD лише у знаменнику та окремій групі. Невідомі перегляди, реакції й дати не перетворюються на нуль. Критичність — пороги правил, не прогноз. Повторення тексту/canonical ID означає поширення, не незалежність підтвердження. Вартість — UI-калькулятор припущень, фінансовий збиток API не вигадує.

Для місяця API читає `core.daily_rollups`, без текстів та запитів до `core.dashboard_items`. Processor перевіряє потребу перебудови раз на 2 секунди; оновлює тільки інвалідовані джерела або покоління старше 60 секунд. Початковий зріз створює міграція. `aggregate_updated_at` показує дату зрізу. Review, нова версія, видалення та reprocess інвалідують відповідні згортки, щоб попередньо прийнятий матеріал не залишився видимим viewer. Таблиця `dashboard_rollup_state` зберігає `dirty` і час покоління; читання агрегатів та coverage відбувається одним SQL snapshot. Якщо хоча б одне джерело інвалідоване, API повертає `aggregation.complete=false`, `metrics.*.value=null`, порожні ряди/розподіли й пояснення перерахунку. Часткові кількості не видаються за повний місячний підсумок. Числа dirty/source доступні тільки операторам; viewer отримує лише стан готовності. У місячному режимі немає окремих текстових сигналів, швидкостей чи аномалій постів; вони доступні у 24h/7d.

## Другий погляд і security-audit

Рішення: **Pass after fixes** для цього пакета. Перевірені Better Auth, серверний RBAC, workflow-фільтри, параметризовані SQL-запити, ліміти ID/вікон, наявний CSRF та відсутність секретів у контракті. Немає нового зовнішнього HTTP або передачі текстів у LLM. Views виконуються власником БД; API має лише SELECT вузьких read models, зміни action/refresh — окремі дозволені таблиці. Security-definer функції мають фіксований `search_path`, `PUBLIC EXECUTE` відкликано.

Self-review знайшов і виправив ризик залишку відхиленого матеріалу в місячному агрегаті; [0013](../db/migrations/0013_dashboard_rollup_invalidation.sql), уточнення [0014](../db/migrations/0014_dashboard_coverage.sql) та regression tests доводять інвалідацію, приховування неповного зрізу й перебудову лише потрібних джерел. Ручне рішення діє тільки для конкретної актуальної версії raw і переживає навмисний reprocess workflow. Baseline переглядів для viewer будується тільки з видимих accepted, тому приховані записи не потрапляють і в знаменник.

Перевірки: повний набір **79 passed** на ufv_checks; `npm run typecheck`, `npm run build`; [tests/test_dashboard.py](../tests/test_dashboard.py) на **ufv_checks** — три ролі, workflow, invalid input, override/version, реакції вручну на трьох постах, невідомі дати, lifecycle коментарів, поширення, drilldown. Окремо місячний endpoint перевірено з відкликаним SELECT на `dashboard_items`: успіх підтверджує відсутність читання сирих текстів. Сканер common secret patterns у новому endpoint/tests — без знахідок. Візуальні ворота виконує потік UI після інтеграції; цей пакет їх не оголошує пройденими.

## «Оновити зараз»

`POST /api/admin/refresh {workflow_id}` та `GET /api/admin/refresh?workflow_id=…` — тільки admin. Відповідь `{requests:[…]}` містить стани `pending/running/completed/deferred/disabled/failed`, часи та українське пояснення. Повторні кліки в межах 30 секунд повертають існуючі запити; одна активна заявка на сервіс/workflow. Дії записуються в audit. API лише пише чергу; працюють чинні автономні collectors.

Telegram перевіряє чергу раз на 2 секунди, RSS — раз на 3. `started_at` означає підхоплення та позачергове планування циклу; завантаження великої черги або джерела може тривати довше. «Оновлено» з'являється тільки після успішних спостережень усіх цільових джерел; processor обробляє нові матеріали окремо. `last_success_at` від планування не змінюється. FloodWait акаунта та Retry-After/backoff RSS збережені; інший акаунт не підставляється. Вимкнений сервіс чи відсутній готовий дозволений доступ повертає `disabled`; очікування лімітів — `deferred`, не фальшивий успіх. Після п'яти хвилин незавершеної черги запит переходить у `deferred`; звичайний збір триває.

Перевірено на ufv_checks: [test_refresh.py](../tests/test_refresh.py) + dashboard — **6 passed**; застосовано реальну роль БД collector без контакту із Telegram/публічними RSS. Прогін із 2-секундним циклом підтвердив підхоплення <5 секунд, окремо перевірені повторні кліки, три ролі, audit, вимкнений модуль, завершення лише за фактом спостереження, збереження FloodWait і RSS retry. Security/self-review: лише фіксовані SQL-фрагменти та bind-параметри; CSRF чинний; секретів/текстів/авторів у заявці немає; ліміти не змінюються.

Для ввімкнення потрібне розгортання API та обох collectors із цією версією; schema/grants уже в 0011. Передано root-агенту, цей пакет сам production-процеси не перезапускає.

## Статус дій

`PUT /api/admin/documents/:mentionId/action {status}` приймає `none/investigating/responding/resolved`; тільки admin, CSRF і audit чинні. Feed та документ повертають `action`, за замовчуванням `none`. Viewer читає статус лише матеріалу, до якого має доступ; analyst/viewer не редагують. Закриття всіх матеріалів групи прибирає її з відкритих сигналів статусу бренду. Це операторська позначка виконаної дії, не доказ фактичного усунення збою.

Self-review з перевіркою реальної API-ролі виявив, що непотрібне `FOR UPDATE` вимагало б UPDATE на mentions. Прибрано блокування; права API не розширено. Зміна власної таблиці й audit атомарні. Перевірено неіснуючий ID (404), неправильний стан (422), чужий Origin (403), дві заборонені ролі, читання viewer, audit і перехід закритого сигналу бренду до спокійного стану. UI-форму й production smoke перевіряє інтеграційний потік.

## Перевірка продуктивності на живому зрізі

Read-only `EXPLAIN ANALYZE` показав, що початковий запит читав 64 390 матеріалів за 7 днів і витрачав 2,62 с. Заміна на accepted/review та вузьку проєкцію до 280 символів цитати дала 4 916 рядків за 0,22 с. Операторські лічильники й точні вибірки затримки тепер рахуються окремим SQL-агрегатом без текстів (24h: 0,068 с). Повний getDashboard нового коду на наступному живому зрізі: 24h — 1,19 с, 7d — 1,46 с; кількості змінюються зі збором. Production не змінювався цими вимірюваннями. Це вимірювання конкретного зрізу, не обіцянка SLA.

## S2 на дашборді

`ai` тепер містить `mode`, `generated_at`, `model`, межі вікна, `observations` із точними цитатами та внутрішнім/оригінальним посиланням, `limitations` і позначку часткового дозволеного покриття. Джерело — тільки `core.current_ai_summaries`; старіша за 30 хвилин генерація/межа вікна не використовується. Метадані snapshot та дозволені докази читаються одним SQL-запитом. Для місяця запиту до текстового `dashboard_items` немає. Неповний monthly generation не показує AI-підсумок.

S2-агрегати можуть включати rejected/pending дозволеного входу, хоча цитати — accepted. Таке зведення цілком недоступне viewer: модельний текст не редагується вибірковим приховуванням чисел. Viewer отримує власний rules fallback. Якщо **весь** модельний вхід accepted, заголовок і всі докази пройшли перевірки, viewer може бачити AI-знімок. URL доказу береться зі сховища; ID перетворюється з raw ID на mention ID, цитата повторно перевіряється як точний фрагмент чинного тексту. Операторський перехід до агрегатних доказів обмежений workflow, джерелами та snapshot-вікном.

`AI очікує ключ` відповідає свіжому `analyst_state.mode=waiting_key`, а не припущенню API. Без heartbeat або після 5 хвилин — `Стан AI-сервісу не підтверджено`; окремо відображаються очікування ліміту, помилка й підготовка. Валідний історичний AI-знімок лишається позначеним `mode=ai` із моделлю/часом; стан runtime не видається за нову модельну генерацію. Читання endpoint не викликає LLM.

[tests/test_dashboard_summary.py](../tests/test_dashboard_summary.py): три ролі, точні докази та їхні переходи, mixed-input viewer fallback, source revoke, review, edit/version, 30-хвилинне старіння, dirty month/recompute, NullProvider і прострочений heartbeat. Разом із попередніми й AI suites: **99 passed** на ufv_checks. WP6 закрито тестом `test_dashboard_metrics_roles_and_drilldown`: три синтетичні пости, NEG=3, IRONIC=3, SAD=8, усі=30; негативна частка вручну `(3+3)/30=20%`. Synthetic fixtures і mock LLM не виходять у production.

Другий погляд/security-audit: параметризовані SQL, read-only S2, role/workflow на endpoint і доказах, whole-summary rejection для невидимого входу, структурна перевірка body, обмеження розмірів/віку, чинні version/rights gates. Підтверджених відкритих дефектів цього інкременту не залишилося; семантична правильність модельних формулювань не доведена exact-quote перевіркою.

Серверний `scripts/import_telegram_sources.py` може перемістити джерело між workflow. `0016_dashboard_source_scope.sql` інвалідує його покоління й прибирає попередні агрегати атомарно із перенесенням. Monthly API додатково звіряє актуальний `sources.workflow_id`; попередній workflow відразу не бачить цих чисел, новий показує перерахунок до нового покоління. Regression на ufv_checks: transfer → old=0/new=pending → recompute → old=0/new=1. Locks використовують порядок state → aggregates, як у processor.

Для refresh API повертає `stale`, `collector_online`, `collector_heartbeat_at`. Pending/running старше 5 хвилин має явне пояснення відсутнього heartbeat або затримки чинної черги. GET не змінює заявку й не вигадує завершення; після повернення collector команда залишається придатною до виконання. Повторний POST теж повертає ці ознаки. UI має прибрати індикатор активного виконання для `stale=true` та показати `detail`. Regression підтвердив missing heartbeat → online heartbeat без підміни pending на completed.

Bootstrap повторює dashboard grants після створення нових runtime-ролей: API insert/update action_status і refresh_requests, collector select/update refresh_requests, processor execute refresh_dashboard_rollups. На ufv_checks виконано саме три SQL-оператори з bootstrap для нових тимчасових ролей: дозволені права підтверджені, зайві DELETE/INSERT відсутні, processor справді виконав функцію. Тимчасові ролі після перевірки видалені. Production bootstrap для цієї перевірки не запускався.

Фінальна перевірка API-потоку після цих змін: TypeScript typecheck/build успішні, **101 passed** на ufv_checks. Self-review refresh: лише admin, SQL параметризований, GET не має записів, POST повторно використовує durable request, перевірка heartbeat не видає успіх за відсутності фактичного завершення. Публічний сервіс і production collector для перевірки не змінювалися.
