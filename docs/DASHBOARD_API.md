# API дашборда: контракт і перевірка

Додано за прямим нічним дорученням користувача. Контракт: [dashboard.ts](../packages/shared/src/dashboard.ts). `GET /api/dashboard?workflow_id=1&window=24h|7d|30d` потребує Better Auth. Admin і analyst бачать accepted/review; viewer — тільки accepted, без відсіяного, pending, загальної кількості входу й плитки шуму. Вікна 24h/7d ковзні; 30d — 30 календарних днів за Києвом включно із сьогодні. `start/end` та `href` фіксують межі для переходів до доказів.

Метрики негативу — словникова евристика, не виміряна тональність. Реакції агреговані за останнім спостереженням: NEG+IRONIC у чисельнику, SAD лише у знаменнику та окремій групі. Невідомі перегляди, реакції й дати не перетворюються на нуль. Критичність — пороги правил, не прогноз. Повторення тексту/canonical ID означає поширення, не незалежність підтвердження. Вартість — UI-калькулятор припущень, фінансовий збиток API не вигадує.

Для місяця API читає `core.daily_rollups`, без текстів та запитів до `core.dashboard_items`. Processor перебудовує згортки раз на хвилину; початковий зріз створює міграція. `aggregate_updated_at` показує дату зрізу. Review, нова версія, видалення та reprocess інвалідують відповідні згортки, щоб попередньо прийнятий матеріал не залишився видимим viewer. До перебудови ці джерела можуть бути тимчасово відсутні; `null`/стара дата зрізу потребує чесної позначки в UI. У місячному режимі немає окремих текстових сигналів, швидкостей чи аномалій постів; вони доступні у 24h/7d.

## Другий погляд і security-audit

Рішення: **Pass after fixes** для цього пакета. Перевірені Better Auth, серверний RBAC, workflow-фільтри, параметризовані SQL-запити, ліміти ID/вікон, наявний CSRF та відсутність секретів у контракті. Немає нового зовнішнього HTTP або передачі текстів у LLM. Views виконуються власником БД; API має лише SELECT вузьких read models, зміни action/refresh — окремі дозволені таблиці. Security-definer функції мають фіксований `search_path`, `PUBLIC EXECUTE` відкликано.

Self-review знайшов і виправив ризик залишку відхиленого матеріалу в місячному агрегаті; [0013](../db/migrations/0013_dashboard_rollup_invalidation.sql) та regression test доводять інвалідацію. Ручне рішення діє тільки для конкретної актуальної версії raw і переживає навмисний reprocess workflow. Baseline переглядів для viewer будується тільки з видимих accepted, тому приховані записи не потрапляють і в знаменник.

Перевірки: повний набір **75 passed** на ufv_checks; `npm run typecheck`, `npm run build`; [tests/test_dashboard.py](../tests/test_dashboard.py) на **ufv_checks** — три ролі, workflow, invalid input, override/version, реакції вручну на трьох постах, невідомі дати, lifecycle коментарів, поширення, drilldown. Окремо місячний endpoint перевірено з відкликаним SELECT на `dashboard_items`: успіх підтверджує відсутність читання сирих текстів. Сканер common secret patterns у новому endpoint/tests — без знахідок. Візуальні ворота виконує потік UI після інтеграції; цей пакет їх не оголошує пройденими.
