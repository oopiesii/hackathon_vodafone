# Перше доопрацювання запитів dashboard

Підстава: незалежний read-only профіль після нічного релізу 19.09.2026; root доручив усунути два виміряні вузькі місця. Це API-зміна без міграції, нових grants або зміни семантичної політики. Production і main під час роботи не змінювалися.

## Зміна

- Для операторських лічильників 24h спочатку матеріалізуються тільки ID, тип джерела й затримка збору з `core.incoming_items` у точному workflow/часовому вікні. Рішення кожного кандидата береться з чинного `core.curated_items`, без дублювання AI/manual/context policy. Тексти, реакції й watch-стан для цього підрахунку не потрібні.
- Приріст переглядів перевіряє поточну видимість цільових матеріалів один раз у materialized CTE, потім приєднує вимірювання в перші дві години включно. Прибрані два корельовані semantic lookup для кожного вимірювання. Повторна перевірка також зберігає workflow, рішення для ролі, часове вікно й активність коментаря, якщо вони змінилися після першої вибірки.
- Для 7d збережений попередній операторський SQL: на нинішній базі тиждень охоплює майже весь вхід, і окремий lookup для кожного запису дорожчий. Це свідоме обмеження оптимізації за вимірюванням; повільні тижневі операторські лічильники лишаються боргом. Місячний фізичний шлях не змінено.

## Вимірювання

Read-only `EXPLAIN (ANALYZE, BUFFERS)` під реальною `ufv_api`, `jit=off`, обмеження одного запиту 10 секунд. Це окремі запити на живій базі під мінливим навантаженням, не SLA та не точний прогноз HTTP-часу.

| Запит | До | Обраний варіант | Примітка |
| --- | ---: | ---: | --- |
| Операторські лічильники 24h | 3276 мс | 1228 мс | Спочатку звужені ID |
| Операторські лічильники 7d | 3801 мс | Без зміни SQL | Кандидат дав 7830 мс; його для 7d відхилено |
| Приріст переглядів 7d | 5777 мс | 33 мс | 0 результатів однаково; раніше 754 × 2 повторних semantic lookup |

Початковий профіль: `/var/tmp/ufv-night-query-profile.json`; кандидат: `/var/tmp/ufv-dashboard-candidate-profile.json`. Файли містять тільки назви планів, числа й часи, без текстів матеріалів або секретів.

## Перевірка й self-review

- Нові інтеграції виконуються лише в `ufv_checks` і через API з runtime-роллю. Перевіряють exact inclusive timestamps, джерела й workflow, accepted/review/rejected/pending/deleted, ручні рішення, застарілі версії та контекст, невідомі/некоректні дати, viewer без операторських чисел.
- Зіставлено оптимізований підрахунок із канонічним `core.curated_items` у часовому вікні, яке повертає API. Приріст перевірено вручну: 4 допустимі вимірювання, 10→130 за 2 години = 60 переглядів/год; вимірювання за межами, null, спад, невидимі й чужі матеріали не створюють приросту.
- Окремо перевірено, що ID з попереднього читання не обходить наступне ручне відхилення або перенесення джерела до іншого workflow. SQL параметризований; прав на raw або нових grants немає. Operator SQL викликається лише для ролей із правом редагування інцидентів.
- Фінальний повний прогін після вибору окремого SQL для 24h/7d: **136 tests PASS, 35,08 с**; API typecheck/build — PASS. Власний runtime API зупинено, `ufv_checks` звільнено. Відтворення на цьому сервері: `npm run build -w @ufv/shared && npm run build -w @ufv/api`, потім `/opt/ufv/.venv/bin/python /tmp/ufv-night-api-test-run.py tests` із цього worktree. Захищений runner запускає API як `ufv_api` на 18203, передає tests окремий `UFV_TEST_ENV` для `ufv_checks` і завершує сервер після тестів; секрети в Git не входять.

Для цього пакета нових міграцій та рестартів worker не потрібно; розгортання API виконує root.
