# План команди

**Актуальний план до пітчу 20.09 — [PLAN_NIGHT.md](PLAN_NIGHT.md); бриф для команди — [TEAM_BRIEF.md](TEAM_BRIEF.md).**

Подальшу деталізацію Telegram за новим запитом користувача див. у [TELEGRAM_NEXT.md](TELEGRAM_NEXT.md). Це кандидатний план: bulk, метрики, lifecycle, аналіз і dashboard; не видавати його за вже виконаний обсяг.

## Мета й поточний інкремент

Широка мета: ранній репутаційний сигнал → пов'язані докази → короткий бриф → рішення комунікаційного менеджера. Поточне пряме доручення звузило перший інкремент до Telegram-модуля з авторизацією, керуванням workflow й нормалізованою стрічкою. Він реалізований; [архітектура й контракти](ARCHITECTURE.md) є вихідною точкою для наступних агентів.

Не переписувати стек. Hono/Better Auth і React уже інтегровані, Telethon потребує Python; PG/NATS виконують узгоджені ролі. Точний дедлайн та навички 7 учасників невідомі; наведені нижче ролі — запропоновані робочі пакети, не призначення конкретних людей.

## Сценарій найближчого демо

Адмін входить → додає власну сесію й дозволений канал → увімкнює workflow → collector зберігає реальний пост і доступні коментарі → processor відсіює шум → користувач відкриває матеріал, контекст та оригінал → адмін виправляє хибний відбір → створює посилання лише на потрібні дані → перевіряє, що його відкликання закриває доступ.

Обов'язково пояснити: коментар може бути доступний лише через polling; накопичені обговорення збільшують затримку; не всі відповіді релевантні; історичні дані не є подіями наживо; збіг тексту не є незалежним доказом. Без дозволу/credentials реальний сценарій ще не готовий, навіть якщо синтетична інтеграція проходить.

## Робочі пакети для 7 учасників

| Роль | Конкретна задача / результат | Залежність |
| --- | --- | --- |
| 1. Інтегратор | Призначити власників, погодити дедлайн, вести STATUS, контролювати контракти, збірку й інтеграцію | Доступність учасників |
| 2. Джерела | Вибрати дозволений реальний канал/випадок, зафіксувати права й походження, перевірити доступ до коментарів | Credentials і умови джерела |
| 3. Collector | Виконати live acceptance, порівняти курсори після рестарту, перевірити редагування/пізні коментарі та фактичну затримку | Роль 2; чинні raw/event контракти |
| 4. Processor / якість | Ручна розмітка невеликої вибірки, розбір false positives/negatives, поліпшення правил і контексту з regression-тестами | Реальні дозволені матеріали |
| 5. API / доступи | Перевірка scope/ролей, підтримка міграцій, передача готового контракту для інцидентів після узгодження їх меж | Чинний Better Auth, рішення інтегратора |
| 6. Frontend | Провести користувача через стрічку/докази/review, перевірити мобільну ширину й помилки; потім інцидент за погодженим контрактом | API і дані ролей 3–5 |
| 7. Продукт / пітч | Обрати роль користувача, описати бізнес-рішення, підготувати 3-хвилинний показ і чесні KPI/обмеження, ручна перевірка | Реальний сценарій і виміри |

## Порядок інтеграції та контрольні точки

Це оцінка наступного циклу після отримання доступів, не фактичний дедлайн:

1. **T0–1 год:** інтегратор підтверджує людей/дедлайн; джерела встановлюють дозволений канал і сценарій. Якщо прав немає — перейти до дозволеного RSS/матеріалу, не обходити умови Telegram.
2. **T+1–3 год:** перевірити на реальних матеріалах повний наявний шлях raw → NATS/processor → API → браузер. Зафіксувати кількість перевірених прикладів і часові мітки. Виправляти тільки виявлені блокери сценарію.
3. **T+3–5 год:** повторний запуск без дублів, пізній коментар, ручний false positive, scoped link і revocation. Зберегти дозволений snapshot з походженням як резерв; не видавати replay за live.
4. **T+5–6 год:** заморозити демо, підготувати обмеження/KPI, двічі прогнати виступ. Якщо фактичний дедлайн 6 год — нові AI-функції не починати.
5. **Лише за наявності другого дня:** погодити межі інциденту і права на AI-обробку. Реалізувати один тип інциденту та бриф, який посилається виключно на збережені ID доказів; окрема ручна перевірка цитат/тверджень. Це наступний обсяг, ще не готова функція.

## Критерії готовності

- Технічні: typecheck/build, integration tests PostgreSQL/NATS/Better Auth, жодних секретів у відповідях, idempotency після повторних подій, обмежений viewer/share, відкликання та відновлення з курсорів.
- Продуктові: принаймні один дозволений реальний наскрізний сценарій; користувач бачить причину відбору й джерело, може виправити помилку; показано реальну затримку цього сценарію без екстраполяції на всі джерела.
- Якість: назвати розмір вручну перевіреної вибірки, кількість помилок і спосіб їх обробки. Не називати rules-v1 AI-моделлю й не вигадувати precision/recall.
- Бізнес: виміряти час від отримання матеріалу до перевіреного рішення оператора; оцінку економії робочого часу порівняти з ручним сценарієм. Невідомі витрати/ефект для Vodafone позначити припущеннями.

Відкладено: прогнозування, автоматичний risk score, граф інцидентів, генерація брифу/відповіді, конкурентний benchmarking, SSO/2FA, автоматичні Telegram/email-сповіщення, приватні канали, мультимодальний аналіз, масштабування collector та автоматичні backups. Не називати зарезервовані таблиці/права готовим продуктом.
