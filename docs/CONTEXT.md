# Контекст і статус рішень

Цей файл фіксує переданий користувачем контекст, а не результати нової перевірки джерел чи моделей. Відповіді на питання зберігаються в [QUESTIONS.md](QUESTIONS.md), перебіг роботи — у [STATUS.md](STATUS.md).

## Мета і межі

Допомогти комунікаційній команді Vodafone збирати реальні відкриті матеріали, визначати релевантність, тональність і причини негативу, виявляти потенційні репутаційні кризи та формувати короткі звіти з доказами й рекомендованими діями.

Умови хакатону згадують прогнозування. Поточний напрям команди — **раннє виявлення сигналів**. Справжня здатність прогнозувати майбутню кризу потребує окремої перевірки й наразі не заявляється.

Команда має 7 учасників, переважно технічних спеціалістів. Попередня оцінка часу — 1–2 дні. Точний дедлайн, доступні години та навички невідомі. В умовах є орієнтир на 6 годин; це не підтверджений дедлайн команди.

## Кандидатний стек — не затверджений

| Компонент | Кандидат | Можлива відповідальність |
| --- | --- | --- |
| Основний backend | Go | HTTP API, конектори за потреби, оркестрація обробки, перевірки, фонові задачі |
| Сховище | PostgreSQL | Матеріали, аналізи, інциденти, докази, збережені задачі |
| Dashboard | React + TypeScript | Стрічка, фільтри, інциденти, докази, дозволені ручні дії |
| Спеціалізовані компоненти | Python лише за конкретної потреби | Бібліотеки збору або аналізу, яких реально потребує обраний сценарій |
| Аналіз тексту | Зовнішній LLM API | Структуроване виділення тверджень, допомога з групуванням і брифом |
| Запуск backend | Один проєкт, процеси `api` та `worker` | Запити користувача окремо від тривалої обробки |
| Черга MVP | Задачі в PostgreSQL | Без обов'язкових Kafka/Redis |

LLM API можна викликати безпосередньо з Go; сам факт використання LLM не вимагає Python-сервісу. Go, Rust, Python та інші варіанти треба оцінити за практичним досвідом учасників, строками й реальною роботою компонентів. Жодна мова не обрана остаточно.

## Обговорена архітектура — не затверджена

1. Конектори RSS/API/HTML повертають спільні поля: `source`, `source_item_id`, `url`, `published_at`, `fetched_at`, `title`, `text`, `content_hash`. Типи, обов'язковість і правила нормалізації ще не визначені.
2. Матеріал для повторної обробки зберігається окремо від висновків моделі. Це необхідний текст, походження й часові мітки, а не безконтрольне збереження HTML. Фільтрацію персональних даних і дозволений обсяг зберігання треба конкретизувати.
3. Звичайний код виконує валідацію, очищення, точну дедуплікацію та обережний попередній відбір. LLM визначає релевантність і виділяє структуровані твердження. Backend перевіряє структуру й наявність цитат у переданому тексті. Відсутні факти залишаються невідомими.
4. Публікація може містити кілька тверджень із різною позицією: наприклад, повідомлення про збій і заперечення оператора. Однієї оцінки тональності для всього матеріалу недостатньо.
5. Інцидент — окрема сутність. Він може містити скарги, новини, спростування, офіційні заяви й повідомлення про відновлення. Поширення новини та незалежні підтвердження обліковуються окремо.
6. Код відбирає можливі інциденти за брендом, темою, часом і локацією; LLM оцінює зв'язок лише з цими кандидатами. Сумнівний матеріал може залишатися неприв'язаним. Межі інциденту та ручні виправлення ще треба визначити.
7. Можливі сутності: `documents`, `analyses`, `incidents`, `incident_evidence`, `jobs`. Це не затверджена схема БД; окрема модель тверджень також потребує рішення.
8. Модель посилається на передані ID доказів. Backend підставляє URL зі збережених джерел. Модель не повинна вигадувати посилання.
9. Фонова обробка потребує збережених задач, повторних спроб та ідемпотентності. Повторний запуск не має дублювати записи або повторно збільшувати лічильники.
10. Розрізняються час публікації, поява в доступному джерелі/агрегаторі, отримання та завершення аналізу. Якщо час появи невідомий, його не вигадують. Polling кожні 5 хвилин не гарантує виявлення через 5–7 хвилин після події; ці числа були прикладом, не вимогою.

## Відкриті рішення та припущення

- Усі [27 питань](QUESTIONS.md) поки без відповідей.
- Не погоджені: точний дедлайн, роль користувача, конкурентний аналіз, мови, джерела, LLM-провайдер/модель, бюджет, деплой, доступ, ручні дії, сповіщення та власники задач.
- Не визначені пороги, оцінка ризику, значення впевненості моделі, baseline для сплесків і цільові показники якості.
- Раніше наведені приклади кількостей згадок, порогів і затримок не є фактичними результатами.
- Історичний випадок для демо не обрано; дозволені реальні матеріали ще треба знайти й перевірити.
- Локальний стан репозиторію перевірено: перед цими документами був лише `README.md`. На інших машинах стан треба перевіряти заново.

## Як фіксувати наступне рішення

Для кожної зміни записати: рішення, статус, підставу або номер відповіді, коротке обґрунтування, вплив на план. Делегований вибір позначати «обрано агентом за делегуванням», а не «користувач обрав».
