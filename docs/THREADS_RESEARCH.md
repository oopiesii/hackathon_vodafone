# Threads як джерело: що реально можливо

Статус: **дослідження, 19.09.2026; нічого не реалізовано.** Підстава — пряме запитання користувача: чи можна через сторонню бібліотеку шукати пости в Threads за ключовими словами й тегами та стежити за ними далі. Висновки спираються на документацію Meta й описи інструментів; жоден інструмент тут не запускався.

## Коротко

Знайти пости за словами — можна, у тому числі офіційно. **Стежити за чужим постом (лічильники, відповіді) офіційно не можна** — це роблять лише неофіційні парсери, які порушують умови Meta й ламаються без попередження. Для пітчу Threads лишається слотом; чесна фраза — нижче.

## Три шляхи

| | Офіційний Threads API | Відкриті парсери | Платні сервіси-парсери |
|---|---|---|---|
| Пошук за словами | так: `GET /keyword_search`, режими `KEYWORD` і `TAG`, сортування `RECENT`, `since`/`until`, до 100 за запит | так, але нестабільно: за одними описами пошук вимагає входу, за іншими — працює без входу з періодичними «стінами входу» | так |
| Ліміт | 2 200 запитів / 24 год на користувача (порожні результати не рахуються); окремі огляди називають 500 / 7 днів — перевірити під час заявки | немає офіційного; на практиці 403 і блокування IP, радять інтервали 5–10 хв | за тарифом сервісу |
| Що повертає | текст, постійне посилання, час, ім'я автора, `has_replies`; **без лайків, відповідей і репостів** | текст, час, лайки, відповіді, репости, самі відповіді | те саме, що парсери |
| Відповіді під чужим постом | у документації є лише керування відповідями під **власними** постами | так | так |
| Доступ | дозвіл `threads_keyword_search` після **App Review Meta**; до схвалення пошук іде лише по власних постах | одразу | одразу, ключ API |
| Стабільність | висока | низька: проєкти на 2–16 зірок, тримаються на прихованому JSON сторінки та гостьових токенах, ламаються після будь-якої зміни Meta | середня: поломки лагодить постачальник |
| Правовий бік | чистий | умови Meta забороняють автоматизований збір без дозволу; авторам неофіційних бібліотек Threads Meta вже надсилала вимоги припинити | той самий ризик + дані йдуть через третю сторону |

Приклади відкритих проєктів: [threadscraper](https://github.com/galihkjaya/threadscraper) (Python, Playwright, гостьові токени GraphQL, автооновлення після трьох 403), [threads-toolkit](https://github.com/Chuanyin1202/threads-toolkit) (TypeScript, по суті актор Apify), розбір техніки — [Scrapfly](https://scrapfly.io/blog/posts/how-to-scrape-threads). Сервіси: актори [Apify](https://apify.com/headply/threads-keyword-search-scraper), SociaVault, SocialCrawl.

## Як це лягає на нашу архітектуру

Модель «пошук кожні 5 хв → закріпитися за постом → стежити до згасання» вже працює для Telegram (`raw.watch_state`, `raw.metric_snapshots`, lifecycle 2–24 дні). Для Threads потрібен лише новий збирач із тим самим контрактом `raw.item.created.v1`:

1. **Виявлення** — офіційний `keyword_search`: 2 200 запитів на добу — це ≈ 7 запитів на кожен 5-хвилинний цикл, достатньо для словника бренду й тем.
2. **Стеження** — повторне читання сторінки поста: лічильники й відповіді. Офіційного способу немає; саме тут починається сіра зона.

Імена авторів, які повертає API, за правилами проєкту не зберігаються.

## Рекомендація

- **Зараз (пітч):** слот «Threads — не підключено». Казати: «Пошук за словами Meta дає офіційно після перевірки застосунку; лічильники й відповіді під чужими постами офіційно недоступні — для них потрібна домовленість із Meta або зовнішній постачальник даних. Наша модель стеження вже працює на Telegram і переноситься без змін».
- **Після пітчу, законний шлях:** подати застосунок на `threads_keyword_search` (потрібна верифікація бізнесу; строк — тижні). Це закриває виявлення. Для корпоративного клієнта на кшталт Vodafone це єдиний шлях без репутаційного ризику.
- **Якщо потрібен доказ концепції:** платний актор Apify замість власного парсера — 2–3 години інтеграції проти 1–2 днів розробки й постійного ремонту. Тільки на тестовій базі, з позначкою «експеримент», без входу в обліковий запис (вхід = ризик блокування акаунта) і з окремим рішенням користувача: це свідоме порушення умов платформи, а за незмінною вимогою проєкту доступність джерела не доводить дозволу на збір.
- **Не робити:** власний парсер із входом у акаунт на production-сервері поруч із робочими Telegram-сесіями.

Варто окремо перевірити (не підтверджено): чи покриває Meta Content Library публічні дописи Threads і чи доступна вона комерційним командам, а не лише дослідникам.
