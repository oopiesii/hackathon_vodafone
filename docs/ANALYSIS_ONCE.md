### Як обробляється весь вхід

1. Snapshot містить ID, версії, нормалізований зміст, часові мітки та зв'язки. Профілі авторів, телефони, сесії й ключі не передаються моделі. До коментаря додається до 8 батьківських відповідей і відомий кореневий пост. Прогалини контексту позначені.
2. Точні повтори однакового типу/тексту/контексту обробляються один раз і отримують окремі результати для кожного запису; цитати й ID контексту перенумеровуються до фактичних джерел. 41 888 різних комбінацій у цьому зрізі. Це економія обробки, не встановлення незалежності доказів.
3. **Кожна комбінація надсилається Gemini 3.8 Flash через AGY** для семантичного відбору. Немає попереднього відсіювання лише за ключовими словами. Батьківський контекст може зробити «у мене теж» тематичним; сам факт коментаря під тематичним постом не робить сторонню суперечку релевантною.
4. Модель повертає тематичні та сумнівні ID; решта отримує результат першого проходу «поза темою». Перевіряються batch ID, кількість переданих елементів, унікальність і належність ID. Самозвіт моделі не доводить правильність семантичного висновку.
5. Тематичні й сумнівні записи проходять детальний аналіз: бренд/галузь, тема, загальний тон, окремі аспекти операторів, причина, цитати з item/контексту, рішення relevant/review/unrelated/spam/ad. Сарказм і невідомі факти не перетворюються на доведені збої. Реклама виключається зі статистики тематичних згадок.
6. JSON і **кожна цитата** перевіряються локально. Relevant і кожен його аспект повинні мати дослівну цитату з самого item; цитати контексту теж звіряються. URL беруться тільки зі збережених джерел.
7. Окремий модельний прохід формує стислий бриф із переданих перевірених прикладів; кожен пункт посилається на існуючі ID. Висновки й рекомендовані перевірки розділені. Статистика рахується по всіх актуальних результатах; текстовий бриф використовує до 80 різних прикладів із пріоритетом Vodafone/коментарів, це позначено в UI.

### Статистика та актуальність

- Пости відокремлені від коментарів/group_message. Тональність коментарів стосується оператора/послуги, а не загального емоційного тону воєнних новин.
- Один коментар може оцінити різних операторів або висловити різні аспекти; суми таблиці операторів не означають кількість людей.
- Перші два джерела — раніше створені користувачем тестові. Їхні матеріали теж аналізуються, але позначаються та не потрапляють у статистику реальних обговорень чи бриф (`scope.test_source_ids`).
- Зміна/видалення item або переданого контексту виключає стару розмітку з поточної статистики. Поява раніше відсутнього прямого батька також робить старий висновок застарілим. Бриф із неактуальним доказом приховується.
- Фільтри релевантності, типу й тону працюють на сервері **до пагінації**; 50 записів на сторінку. Статистика охоплює весь зріз, не лише видимі картки.
- `/analysis` оновлює результати кожні 15 секунд тільки поки run=running. Дані залишаються на екрані між запитами; це не новий LLM-запуск і не повторне повне завантаження сторінки.
- Настрої зібраних коментарів **не представляють усіх абонентів**. Повноту покриття, точність, незалежність доказів та прогнозування криз не виміряно.

## Контракти та збереження

- Нова застосована міграція **0009_analysis_once.sql**: `core.analysis_runs`, `core.analysis_labels`, `core.search_briefs`. Не редагувати після застосування.
- Розмітка окрема від `raw.items`, `core.mentions` та `core.review_decisions`. Звичайний processor не переписує її і продовжує показувати свою стрічку за правилами.
- Run має workflow, cutoff, модель, версію prompt, scope, total і статус. Кожен результат має ID/версію матеріалу, класифікацію, короткий виклад, пояснення і докази. ID/версії всіх переданих батьків зберігаються для перевірки актуальності.
- Пакети до 20 елементів і приблизно 60 KB; максимум три спроби. Контрольні файли для повторного запуску — поза Git, у `/var/lib/ufv/analysis-once/rss-20260919`, права 0700/0600. Повторний запуск того самого state-dir відновлює той самий зріз; upsert не множить результати.
- JSON перевіряється локально: точні типи/enum/поля, всі очікувані ID рівно один раз, кожна цитата має бути підрядком наданого матеріалу/контексту. Релевантність без доказу із самого item відхиляється. Це перевірка цілісності доказів, не гарантія правильного висновку.
- API отримує оригінальні URL із `core.incoming_items`; модель не створює посилань. Якщо матеріал або будь-який переданий контекст видалений/змінив версію, розмітка не входить до поточної статистики. У списку результати з однаковим URL об'єднані, лічильники показують записи; незалежність доказів не встановлюється.
- AGY працює в окремому файловому просторі через `bwrap`, із власним тимчасовим config/cache і заборонами file/command/MCP/web-інструментів. Production DSN та ключі не передаються до subprocess. Глобальні налаштування інших CLI-сесій не змінюються. Тимчасова копія AGY-авторизації видаляється після запуску.

## Пошук

[Добірка за 19 вересня](data/search-2026-09-19.json) містить короткі цитати, власні перекази, дати, джерела та межі перевірки. Для чотирьох офіційних повідомлень цитати додатково звірені з українським HTML на сервері. The Page перевірено через інструмент вебчитання; прямий HTTP із сервера повертає 403, обходу обмеження не робили.

`scripts/import_search_briefs.py` імпортує перевірену добірку через `DATABASE_URL` із захищеного оточення. Повторний імпорт тієї самої дати/URL не створює дубль. **Автоматичного щоденного пошуку/таймера немає**; UI явно показує це. Не називати цей разовий результат live-моніторингом або автоматичним пошуковим конектором. Повні тексти статей і авторські профілі не зберігаються.

## Чому змінюється «Увесь вхід»

Inbox запитує API кожні 5 секунд, Feed — кожні 30; це оновлення даних React, а не обов'язкове повне перезавантаження документа. Колектор дочитує історію та коментарі 66+ підключених джерел. Новий item або нова версія спочатку pending, після processor — accepted/review/rejected. Зміна батьківського контексту чи workflow revision також потребує повторної обробки. На перевірках о 19:30 і після цього релізу pending=0: постійного завислого backlog не виявлено. Це не обіцянка нульової черги в кожну мить.

Повернення старого образу не потребує видалення доданих таблиць або відновлення старої БД.

Цей нижній розділ описує попередній RSS-реліз. Актуальний стан Telegram наведено на початку документа; автоматичний щоденний пошук, безперервний LLM-пайплайн, ручна оцінка якості та інциденти залишаються окремими задачами.
