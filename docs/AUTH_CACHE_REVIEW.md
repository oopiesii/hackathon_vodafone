# Ізоляція кешу після зміни доступу

Дата: 2026-09-19. Незалежна перевірка нічного UI, без production і без `ufv_checks`.

## Підтверджений дефект

У Chromium із синтетичним API послідовність admin → «Вийти» → viewer у тій самій вкладці з помилкою нового GET `/dashboard` залишала адміністративне зведення та показник «Відсіяний шум». Причина: глобальний `QueryClient` переживав зміну сеансу, а ключі dashboard/feed не містили ідентичності доступу. Серверний RBAC не запобігає показу вже отриманого клієнтського кешу.

## Зміна

- Глобальний кеш вилучено. Ідентифікатор сеансу Better Auth, користувач і роль визначають окремий життєвий цикл кешу `/me`.
- Після підтвердження `/me` дані застосунку отримують власний `QueryClient`, прив'язаний до користувача, ролі та фактичних permissions. Зміна дозволів перемонтовує subtree до показу старих даних; перевірка `/me` повторюється щохвилини та при фокусі вкладки.
- Помилка перевірки `/me` приховує приватний subtree і пропонує повторити запит або вийти.
- Запізнілий HTTP-запит завершується лише у старому клієнті. Його результат не має шляху до нового кешу.
- `/view` має незалежний кеш на кожне відкриття нового посилання. Окремо враховується native hash navigation, яка може повторити history key. Реальний token не входить до query key. Після зміни посилання його доступ перевіряється знову; зміна фільтрів зберігає вже підтверджену прив'язку.
- На недійсному `/view` прибрано дубль пояснення помилки.

Межа: UI реагує на зміну ролі після її отримання від сервера; права кожного HTTP-запиту, як і раніше, перевіряє API. Поточні запити попереднього сеансу не скасовуються сервером, але їхні дані недоступні новому subtree.

## Відтворювана перевірка

```sh
npm run build -w @ufv/shared
npm run build -w @ufv/web
node scripts/check_auth_cache_browser.mjs
```

Скрипт використовує тільки loopback HTTP, production bundle та синтетичні відповіді; не читає секретів, БД чи production. Перевіряє затриманий і невдалий GET після admin → viewer, завершення старого admin-запиту, зниження прав у тому самому сеансі, помилку `/me`, зміну публічного посилання без перезавантаження документа та єдине пояснення недійсного посилання. Знімки зберігаються в ігнорованому `artifacts/auth-cache/`; мобільні стани додатково перевіряються на горизонтальне переповнення.

## Прив'язка спільного доступу до посилання

Другий аудит підтвердив окрему гонку: POST `redeem` широкого посилання затримано → вузьке посилання завершило вхід → пізній `Set-Cookie` широкого посилання замінив cookie → оновлення вузької стрічки отримало широкий текст. Ізоляція React-кешу сама по собі не захищає cookie, спільну для вкладок.

API `redeem` та `/shared/me` тепер повертають несекретний `scope_id` посилання. Відразу після redeem `/me` отримує заголовок `x-ufv-share-scope`; усі наступні shared feed/document/logout-запити мусять надсилати цей ідентифікатор. Він не надає жодних прав: API спочатку перевіряє cookie, строк і відкликання, а потім збіг ідентифікатора. Невідповідність або відсутність прив'язки для даних повертає `409 share_scope_changed`, без матеріалів. Вхід на `/view` без нового token може один раз прочитати поточну cookie через `/me`; надалі цей scope незмінний до відкриття іншого посилання.

Query-параметри не перемонтовують shared boundary і не перечитують cookie без прив'язки. Інакше зміна пошукового фільтра могла б прийняти пізню широку cookie за новий scope. Повторне відкриття потрібного посилання навмисно поновлює доступ.

`node scripts/check_shared_race_browser.mjs` використовує справжні HttpOnly cookies Chromium та переставляє порядок синтетичних HTTP-відповідей: пізня широка cookie не розширює feed; document-запит зберігає вузьку прив'язку; зміна фільтра не читає незв'язаний `/me`; повторне відкриття вузького посилання відновлює його scope. Усі 4 перевірки пройшли. Попередні 7 auth-cache регресій збережені.

На окремій `ufv_checks` під власним API перевірено `test_roles_origins_share_scope_revocation` і `test_shared_requests_bound_to_redeemed_link`: **2 passed**, включно з відсутнім заголовком, застарілою широкою cookie, `/me`, feed, фільтрами, documents, scope та відкликанням. Production не змінювався.

Сумісність: цей контракт потребує одночасного оновлення API та web; старий клієнт без заголовка не отримає shared-дані й мусить перезавантажити сторінку.
